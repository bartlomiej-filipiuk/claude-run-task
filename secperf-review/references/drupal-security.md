# Drupal security

Drupal 10/11 custom code. OWASP Top 10 (2025) and OWASP API Security Top 10 (2023).

Each item: severity is the default; `severity.md` escalation and downgrade rules apply. Report a pattern only when "Not a finding when" does not hold for the code you read.

### DSEC-01 · Route opened with _access: 'TRUE' or gated only by 'access content' / _user_is_logged_in

**Severity:** high · **Area:** security · **Taxonomy:** A01:2025, API5:2023, CWE-862 · **Applies to:** Drupal 10 and 11

**Signals:** New or changed *.routing.yml entries (or RouteSubscriber alterRoutes / Route objects in PHP) with `_access: 'TRUE'`, `_permission: 'access content'`, or `_user_is_logged_in: 'TRUE'` as the only requirement on routes whose path or controller writes data, returns non-public data, exports, triggers mail/cron/imports, or sits under /admin or /api. Also `$route->setRequirement('_access', 'TRUE')` and `$route->setRequirements([])` in route subscribers.

**Why:** A route with no requirements fails closed (403), so developers often 'fix' it with _access: 'TRUE' or a permission every visitor has. Any anonymous or authenticated user can then call the controller directly. This is broken function-level authorization.

**Fix:** Pick a dedicated permission (declare it in *.permissions.yml) or use _entity_access / _custom_access that checks the actual object. Example: `requirements: { _permission: 'administer my_module' }` or `_entity_access: 'node.update'`. For machine endpoints (webhooks), keep _access: 'TRUE' only if the controller checks an HMAC signature or shared secret with hash_equals() before doing anything.

**Not a finding when:** Truly public endpoints are fine: public listing/landing pages, sitemap, robots, RSS, health checks returning no data, OAuth/SSO callback routes, webhooks that verify a signature in the first lines of the controller. 'access content' is correct for read-only views of published public content. A route with no requirements at all is a functional bug (403), not a hole. Routes generated by entity route providers (DefaultHtmlRouteProvider/AdminHtmlRouteProvider) already carry _entity_access or admin_permission.

**Also check:** _permission comma versus plus semantics in routing.yml: `_permission: 'a,b'` requires BOTH, `'a+b'` requires ONE, so `access content+administer x` silently opens a route to everyone (PermissionAccessCheck, verified). Same idea for `_role`. Source: https://api.drupal.org/api/drupal/core!modules!user!src!Access!PermissionAccessCheck.php/function/PermissionAccessCheck::access/11.x

**Sources:** https://www.drupal.org/docs/8/api/routing-system/access-checking-on-routes · https://api.drupal.org/api/drupal/core!lib!Drupal!Core!Access!AccessManager.php/function/AccessManager::check/11.x · https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/

### DSEC-02 · Upcast entity route parameter protected only by a generic permission (BOLA/IDOR)

**Severity:** high · **Area:** security · **Taxonomy:** A01:2025, API1:2023, CWE-639 · **Applies to:** Drupal 10 and 11

**Signals:** routing.yml path containing `{node}`, `{user}`, `{media}`, `{commerce_order}`, `{my_entity}` or `options: parameters: x: type: entity:...` where requirements have `_permission:` / `_user_is_logged_in` but no `_entity_access:` and no `_custom_access:`, and the controller does not call `$entity->access('view'|'update'|'delete')`. Also custom `_entity_form:` routes without `_entity_access`.

**Why:** Any user who has the generic permission can change the ID in the URL and read or modify someone else's order, profile, submission or unpublished node. This is a common access bypass class in contrib modules.

**Fix:** Add `_entity_access: 'node.view'` (entity parameter name + operation), or a `_custom_access` checker that receives the upcast entity and returns `$entity->access('update', $account, TRUE)` together with an ownership check. Example: `requirements: { _entity_access: 'order.view' }`.

**Not a finding when:** Admin-only routes whose permission already grants access to all entities of that type (for example 'administer nodes' or the entity type's admin_permission) do not need a per-entity check. Config entities managed only by admins are the same. Also check the controller body: an explicit `$entity->access()` call with an AccessDenied exception is equivalent. Routes from entity route providers already include _entity_access.

**Also covers DEC-04 (Custom REST, controller or GraphQL resolver for the frontend skips entity access).** Signals: ->accessCheck(FALSE) in code reachable from a route; getStorage()->load($id) or loadByProperties(['uuid'=>...]) followed by JsonResponse, CacheableJsonResponse or ResourceResponse with no ->access('view'); *.routing.yml with _access: 'TRUE' under /api/; a RestResource (@RestResource or #[RestResource]) whose get() loads an entity and returns it without ->access('view'), or that overrides permissions() or routes() to drop the generated permission; GraphQL ->produce('entity_load')->map('access', $builder->fromValue(FALSE)); custom DataProducer that loads entities directly Not a finding when: accessCheck(FALSE) is fine for counts or aggregates that are not returned, and in cron, queue or drush code. It is also fine when the query already filters status=1 on an entity type without node grants and the endpoint serves only published data. Config entities with no view restriction are fine. A RestResource alone is not a finding: the REST module generates a required permission per resource and method, so flag only a missing entity access check in the method body or a removed permission.

**Also covers DSEC-05 (Entity loaded by ID from request or body in controller/REST/GraphQL/JSON endpoint without access check).** Signals: `->load($request->get(...))`, `->load($id)` / `loadMultiple($ids)` / `loadByProperties([...])` where $id comes from route string param, query, JSON body or GraphQL args; classes extending ResourceBase (#[RestResource] / @RestResource) with get()/patch()/delete(); GraphQL DataProducer plugins (`#[DataProducer]`, `resolve(`) calling storage load; controllers returning JsonResponse/CacheableJsonResponse built from loaded entities; no `->access(` nearby. Not a finding when: Loads of entities that belong to the current user by construction (`User::load($this->currentUser->id())`), loads for internal processing whose output is not returned, and loads inside admin-only routes are fine. JSON:API and core REST entity resources already check entity and field access. Only custom resources, controllers and resolvers need this.

**Sources:** https://www.drupal.org/docs/8/api/routing-system/access-checking-on-routes · https://www.drupal.org/docs/8/api/routing-system/access-checking-on-routes/advanced-route-access-checking · https://api-security.owasp.org/editions/2023/en/0x11-t10 · https://www.drupal.org/sa-contrib-2018-071 · https://git.drupalcode.org/project/graphql/-/blob/8.x-4.x/src/Plugin/GraphQL/DataProducer/Entity/EntityLoad.php · https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/ · https://www.drupal.org/docs/core-modules-and-themes/core-modules/jsonapi-module/security-considerations

### DSEC-03 · Custom access checker with wrong logic, role/uid checks, or missing cacheability

**Severity:** high · **Area:** security · **Taxonomy:** A01:2025, CWE-285 · **Applies to:** Drupal 10 and 11

**Signals:** Classes implementing AccessInterface / `_custom_access` callbacks / hook_entity_access / hook_ENTITY_TYPE_access / blockAccess(). Look for: `return TRUE;` or bool returns; `AccessResult::allowed()` returned without `->cachePerUser()`, `->cachePerPermissions()` or `->addCacheableDependency($entity)` when the decision depends on user or entity; `hasRole('administrator')`, `id() == 1`, `$account->isAuthenticated()` as the only rule; `orIf` where `andIf` is meant; hook_entity_access returning `AccessResult::allowed()` broadly (it overrides neutral results from other modules).

**Why:** A wrong decision opens objects to the wrong users. Missing cache contexts are worse: the first user's access result is cached and reused for other users (render cache, dynamic page cache), so private content leaks or legitimate users get 403 at random.

**Fix:** Return AccessResultInterface. Use `AccessResult::allowedIfHasPermission($account, 'x')`, which adds the permissions context. For ownership: `AccessResult::allowedIf($entity->getOwnerId() == $account->id())->cachePerUser()->addCacheableDependency($entity)`. Return neutral rather than allowed when the hook has no opinion. Base checks on permissions, not role names or uid 1.

**Not a finding when:** allowedIfHasPermission()/allowedIfHasPermissions() already add cachePerPermissions. Access results used only in non-cached contexts (form submit, drush, queue) do not need cacheability. hook_entity_access returning neutral() is correct and should not be flagged. Checking uid 1 inside a drush command or update hook is fine.

**Sources:** https://www.drupal.org/docs/8/api/routing-system/access-checking-on-routes/custom-route-access-checking · https://api.drupal.org/api/drupal/core!lib!Drupal!Core!Access!AccessResultNeutral.php/class/AccessResultNeutral/11.x

### DSEC-04 · Entity query with accessCheck(FALSE) whose results reach the current user

**Severity:** high · **Area:** security · **Taxonomy:** A01:2025, API1:2023, CWE-862 · **Applies to:** Drupal 9.2+ (warning), Drupal 10 and 11 (exception if missing); content entities only

**Signals:** `->accessCheck(FALSE)` in controllers, blocks, forms, REST/GraphQL resolvers, Views plugins, autocomplete handlers, or services called from them; `getQuery()`/`entityQuery()` without any accessCheck (throws in D10+, flag as a bug); `->accessCheck(TRUE)` on custom entity types followed by rendering without `$entity->access('view')`.

**Why:** accessCheck(FALSE) skips node grants and query access alters. Unpublished or private entities (other users' orders, restricted groups) then show up in lists, autocomplete and API output. accessCheck(TRUE) only applies query-level alterations (node grants and whatever the entity type implements). For most custom entity types it does not run the access control handler per entity.

**Fix:** Use `->accessCheck(TRUE)` for anything shown to or returned for a user. If the entity type has no query access, filter the loaded entities: `array_filter($entities, fn($e) => $e->access('view'))`. Keep accessCheck(FALSE) for system code only and add a one-line comment saying why.

**Not a finding when:** accessCheck(FALSE) is correct in cron, queue workers, drush commands, migrations, update/post_update hooks, event subscribers doing system bookkeeping, uniqueness checks, counters that are not displayed, and code that checks $entity->access() right after loading. Config entity queries do not need accessCheck at all (confirmed by the change record).

**Sources:** https://www.drupal.org/node/3201242 · https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/

### DSEC-06 · Custom JSON output built with toArray()/getValue() leaks fields the user may not see

**Severity:** medium · **Area:** security · **Taxonomy:** A01:2025, API3:2023, CWE-200, CWE-213 · **Applies to:** Drupal 10 and 11

**Signals:** `$entity->toArray()`, `->get('field_x')->getValue()` / `->value` in a loop over `getFields()`, `json_encode($entity...)`, `new JsonResponse($user->toArray())`, custom normalizers extending NormalizerBase that iterate fields without `->access('view')`; any output that includes the user entity (`pass`, `mail`, `init`, `roles`, `status`), or fields like `field_internal_notes`, `revision_log`.

**Why:** toArray() and getValue() ignore field access. User entities expose the password hash and email this way. Other entities expose internal or moderation fields. Core's own normalizers skip fields without view access, and custom code bypasses that protection.

**Fix:** Use the serializer (`$serializer->normalize($entity, 'json', ['account' => $account])`), which checks field view access in ContentEntityNormalizer, or build an explicit allowlist and check `$entity->get($name)->access('view', $account)` for each field. Never serialize the user entity directly.

**Not a finding when:** Explicit allowlists of harmless fields (id, label, url) on entities the user can view are fine. toArray() used for internal processing, caching, cloning or migrations that is never returned to the client is fine. JSON:API, core REST and GraphQL schema fields go through field access.

**Sources:** https://api.drupal.org/api/drupal/core!modules!serialization!src!Normalizer!ContentEntityNormalizer.php/function/ContentEntityNormalizer::normalize/11.x · https://api.drupal.org/api/drupal/core!modules!user!src!UserAccessControlHandler.php/function/UserAccessControlHandler::checkFieldAccess/11.x · https://api-security.owasp.org/editions/2023/en/0x11-t10

### DSEC-07 · Mass assignment: request data written to entity fields without allowlist or field edit access

**Severity:** high · **Area:** security · **Taxonomy:** A01:2025, API3:2023, API6:2023, CWE-915 · **Applies to:** Drupal 10 and 11

**Signals:** `Entity::create($request->request->all())`, `Node::create($data)` with $data from json_decode of the body, `foreach ($data as $key => $value) { $entity->set($key, $value); }`, `$entity->set($request->get('field'), ...)`, GraphQL mutation producers that copy input arrays into entities; no `->access('edit')` per field and no `$entity->validate()` before `save()`.

**Why:** The client can set fields it should not control: uid (ownership), status/promote, moderation_state, roles, price or discount fields, and entity references to other users' data. Entity validation constraints are not run by save(), so invalid references also get stored.

**Fix:** Allowlist the writable fields. For each field check `$entity->get($name)->access('edit', $account)`. Call `$violations = $entity->validate()` and reject on errors before `save()`. Set uid/status on the server side.

**Not a finding when:** A fixed list of field names defined in code, fields set from trusted server values, admin-only import tools and migrations are fine. Form API entity forms (ContentEntityForm) already apply widget-level field access and validation.

**Also covers DSEC-32 (User entity privilege changes (roles, status, password, email) from request data without checks).** Signals: `$user->addRole($request->get(...))`, `->addRole('administrator'|'editor')` in public registration, webhook or SSO handlers; `$user->activate()` or `->set('status', 1)` in anonymous flows; `$user->setPassword($new)` or `->setEmail($x)` without `setExistingPassword()` / current password verification; `User::create([... 'roles' => $input ...])`; SSO/OAuth handlers mapping remote claims straight to roles; `$user->set('mail', ...)` or `->set('name', ...)` from input without `validate()` (uniqueness constraints only run on validate; compare SA-CORE-2024-004). Not a finding when: Drush commands, update hooks and admin-only forms behind 'administer users' are fine. Assigning a fixed low-privilege role on registration (for example 'customer') is normal.

**Sources:** https://api-security.owasp.org/editions/2023/en/0x11-t10 · https://www.drupal.org/docs/core-modules-and-themes/core-modules/jsonapi-module/security-considerations · https://top10.owasp.org/2025/A07_2025-Authentication_Failures/ · https://www.drupal.org/sa-core-2024-004

### DSEC-08 · State-changing GET route without CSRF token

**Severity:** high · **Area:** security · **Taxonomy:** A01:2025, CWE-352 · **Applies to:** Drupal 10 and 11

**Signals:** routing.yml route with no `methods: [POST]` (or with GET) whose controller calls `->save()`, `->delete()`, flags/follows/subscribes, changes status, sends mail, clears caches, or logs out, and has no `_csrf_token: 'TRUE'`. Links to such routes built as string paths (`'/my/path/' . $id`) instead of `Url::fromRoute()` (token not added). `_csrf_request_header_token` on a GET route.

**Why:** An attacker can embed the URL in an image tag or link. A logged-in admin who opens the page triggers the action with their own session (delete content, grant roles, unpublish).

**Fix:** Add `_csrf_token: 'TRUE'` and generate the link with `Url::fromRoute('route', $params)` so the token is appended. Optionally add the route option `_csrf_confirm_form_route: 'my.confirm_route'` so a missing token lands on a confirmation form instead of a 403 (this is how core logout works since 10.3). Better, use a ConfirmFormBase form (Form API adds form_token) or a POST route. For JSON endpoints with cookie auth use `_csrf_request_header_token: 'TRUE'` with methods [POST, PATCH, DELETE] plus a real access check, because the header check always passes for anonymous users.

**Not a finding when:** Idempotent read-only GET routes, Form API forms (they carry form_token), ConfirmFormBase flows, and routes that already have _csrf_token are fine. _csrf_token fails for users without a session, so anonymous-facing actions need a form or a different design. Do not flag it as missing where it would break the feature without saying so. Core logout has used a CSRF token with a confirm-form fallback since 10.3; custom logout links should reuse the core route via Url::fromRoute.

**Sources:** https://www.drupal.org/docs/8/api/routing-system/access-checking-on-routes/csrf-access-checking · https://api.drupal.org/api/drupal/core!lib!Drupal!Core!Access!CsrfAccessCheck.php/class/CsrfAccessCheck/11.x · https://www.drupal.org/node/2822514 · https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/

### DSEC-09 · Form trusts client-controlled values (hidden #default_value, getUserInput, raw request)

**Severity:** medium · **Area:** security · **Taxonomy:** A01:2025, A06:2025, CWE-472, CWE-20 · **Applies to:** Drupal 10 and 11

**Signals:** `'#type' => 'hidden'` with `'#default_value' => $id|$price|$role|$uid` that submitForm() then uses to load or save; `$form_state->getUserInput()` in validateForm/submitForm; `\Drupal::request()->request->get()` or `$_POST` inside forms; security relying on `'#disabled' => TRUE`, `'#attributes' => ['readonly' => ...]` or JS to prevent edits.

**Why:** Hidden field values with #default_value can be changed in the browser. getUserInput() returns raw, unvalidated input that skips Form API checks such as the 'illegal choice' check for select/radios. The user can then act on another user's entity or change prices and roles.

**Fix:** Use `'#type' => 'value'` (never sent to the browser) or `'#value'` (Form API enforces it), or keep the value in `$form_state->set()`/`getStorage()`. Read input only with `$form_state->getValue()`. Re-check access to the target entity in submitForm.

**Not a finding when:** Hidden fields that only carry UI state for JS and are re-validated or re-derived on the server are fine. getUserInput() inside #ajax callbacks that only rebuild the UI (no save) is common and acceptable. Hidden #value (not #default_value) is enforced by Form API.

**Sources:** https://api.drupal.org/api/drupal/core!lib!Drupal!Core!Form!FormStateInterface.php/function/FormStateInterface::getUserInput/11.x · https://api.drupal.org/api/drupal/core!lib!Drupal!Core!Render!Element!Hidden.php/class/Hidden/11.x · https://api.drupal.org/api/drupal/core!lib!Drupal!Core!Render!Element!Value.php/class/Value/11.x

### DSEC-10 · form_alter overrides field access or removes validation

**Severity:** medium · **Area:** security · **Taxonomy:** A01:2025, CWE-285 · **Applies to:** Drupal 10 and 11

**Signals:** In hook_form_alter / hook_form_FORM_ID_alter / #[Hook('form_alter')] methods: `$form['roles']['#access'] = TRUE`, `$form['status']['#access'] = TRUE`, `$form['field_x']['#access'] = TRUE` without a permission check; `$form['#validate'] = [...]` (replacing instead of appending), `unset($form['#validate'])`, `unset($form['actions']['submit']['#validate'])`, `'#limit_validation_errors' => []` on a button whose #submit saves data; removed `#element_validate`.

**Why:** Entity forms set #access from field access and permissions. Forcing it to TRUE lets ordinary users edit roles, status, owner or moderation fields. Replacing #validate drops core validators (for example the user form's password and name checks).

**Fix:** Make #access conditional: `$form['x']['#access'] = $account->hasPermission('...')`. Append validators: `$form['#validate'][] = '::myValidate'` or `array_unshift`. Keep #limit_validation_errors only on buttons that do not persist data (such as 'Add another item').

**Not a finding when:** Setting #access to FALSE (hiding) is safe. Setting TRUE under an explicit permission or role-management check is fine. Replacing #validate in a form the module owns (its own FormBase) is normal. #limit_validation_errors on AJAX add-more/remove buttons is standard.

**Sources:** https://api.drupal.org/api/drupal/core!lib!Drupal!Core!Form!FormState.php/function/FormState::setLimitValidationErrors/11.x · https://www.drupal.org/docs/security-in-drupal/writing-secure-code-for-drupal

### DSEC-11 · SQL built by string concatenation in query()/where()/addExpression()

**Severity:** critical · **Area:** security · **Taxonomy:** A05:2025, CWE-89 · **Applies to:** Drupal 10 and 11

**Signals:** `->query("...$var...")`, `->query('... ' . $x)`, `->where('... ' . $x)`, `->addExpression('... ' . $x)`, `->having('...' . $x)`, `sprintf` into SQL, `{$table}` interpolated from user input; legacy `db_query(` (removed before Drupal 9, a sign of ported code).

**Why:** Concatenated values allow SQL injection, which can mean full database read, privilege escalation or RCE. The Drupal DB layer only protects values passed as placeholders.

**Fix:** Use named placeholders: `$db->query('SELECT nid FROM {node_field_data} WHERE title = :t', [':t' => $title])`, or the query builder `->condition('title', $title)`. For IN lists use `:ids[]` with an array. Take table and field names from code constants or an allowlist, never from input.

**Not a finding when:** Concatenating constants, class properties set in code, `{table}` names from code, and values cast with `(int)` right before use is fine (still prefer placeholders). `$connection->escapeTable()/escapeField()` on allowlisted names is fine.

**Sources:** https://www.drupal.org/docs/administering-a-drupal-site/security-in-drupal/writing-secure-code-for-drupal · https://top10.owasp.org/2025/A05_2025-Injection/

### DSEC-12 · User-chosen operator, field name or sort key in condition()/orderBy()

**Severity:** medium · **Area:** security · **Taxonomy:** A05:2025, A01:2025, CWE-89, CWE-639 · **Applies to:** Drupal 10 and 11

**Signals:** `->condition($field, $value, $request->get('op'))`, `->condition($request->get('field'), ...)`, `->orderBy($request->query->get('sort'), $request->query->get('order'))`, `->sort($userField)` on entity queries, `->fields('u', $userList)`, Views/exposed-filter-like custom code taking operator strings from input.

**Why:** Core rejects operators containing UNION or [-'"(); and escapes field names, and forces sort direction to ASC/DESC, so this is rarely raw SQLi today. But a user-chosen operator ('<>', 'IS NOT NULL', 'NOT IN') can return rows the query was meant to exclude. A user-chosen field lets the attacker filter or sort by sensitive columns (pass, mail, token) and extract them one bit at a time.

**Fix:** Map input to an allowlist: `$ops = ['eq' => '=', 'gt' => '>']; $op = $ops[$input] ?? '=';` and `$sortable = ['title', 'created']; if (!in_array($sort, $sortable, TRUE)) { $sort = 'created'; }`.

**Not a finding when:** Operators and fields chosen from a hardcoded map or in_array(..., TRUE) allowlist are fine. Direction strings passed to orderBy() are normalized by core and are not a risk alone.

**Sources:** https://api.drupal.org/api/drupal/core!lib!Drupal!Core!Database!Query!Condition.php/function/Condition::compile/11.x · https://api.drupal.org/api/drupal/core!lib!Drupal!Core!Database!Query!Select.php/function/Select::orderBy/11.x · https://www.drupal.org/docs/administering-a-drupal-site/security-in-drupal/writing-secure-code-for-drupal

### DSEC-14 · Twig output with |raw, autoescape false, or |t on variables

**Severity:** high · **Area:** security · **Taxonomy:** A05:2025, CWE-79 · **Applies to:** Drupal 10 and 11 (Twig 3)

**Signals:** *.html.twig diffs with `|raw`, `{% autoescape false %}`, `{{ variable|t }}` (variable without literal string), `{{ node.field_x.value|raw }}`, `{{ user_input|striptags|raw }}`; SDC *.twig in components/ with |raw on props.

**Why:** Drupal Twig escapes everything by default, and |raw turns that off. A field value, config string or query parameter printed with |raw runs attacker JavaScript in admins' browsers (session takeover, adding admin users). The |t filter returns translatable markup that is treated as safe, so passing a variable to it skips escaping; the Drupal docs say passing a variable directly to translation is unsafe.

**Fix:** Print render arrays (`{{ content.body }}`) or `.processed` for formatted text. Remove |raw; if HTML is needed, filter it in PHP with a text format (`'#type' => 'processed_text'`) and pass a render array. For dynamic text in a sentence use `{{ 'Hello @name'|t({'@name': name}) }}` or `{% trans %}` with placeholders, or `|placeholder` to escape and emphasize.

**Not a finding when:** `|raw` on values that are already render arrays or Markup objects (`content.*`, `rendered`, output of `|render`, strings built with `t()` in preprocess) does not add risk. It is redundant, not a vulnerability. |raw on literals defined in the template or on `|json_encode` output in a script tag with a constant structure is fine. Check preprocess before flagging. Printing `{{ item.value }}` of a formatted field without `.processed` is escaped (a display bug, not XSS). `|t` on a variable holding a code literal (plugin label) is a style smell.

**Sources:** https://www.drupal.org/docs/theming-drupal/twig-in-drupal/filters-modifying-variables-in-twig-templates · https://www.drupal.org/docs/administering-a-drupal-site/security-in-drupal/writing-secure-code-for-drupal · https://top10.owasp.org/2025/A05_2025-Injection/

### DSEC-15 · User data wrapped as trusted markup (Markup::create, FormattableMarkup string, #markup, wide #allowed_tags, filterAdmin on public input)

**Severity:** high · **Area:** security · **Taxonomy:** A05:2025, CWE-79 · **Applies to:** Drupal 10 and 11

**Signals:** `Markup::create($x)`, `new FormattableMarkup($userString, ...)`, `ViewsRenderPipelineMarkup::create`, `'#markup' => $entity->get('field')->value`, `'#markup' => $request->get(...)`, `'#markup' => $config->get('text')`, `'#allowed_tags' => [... 'iframe'|'svg'|'object'|'form' ...]`, `Xss::filterAdmin($value)` on content from non-admin users, `'#children' => $string`.

**Why:** Markup::create() marks a string as safe, so nothing escapes it afterwards. #markup goes through Xss::filterAdmin, which allows all tags usable inside an HTML body except script and style. That is enough for phishing, layout injection and often attribute-based payloads. Widening #allowed_tags can re-enable dangerous tags. Core itself had to harden the XSS filter (SA-CORE-2026-011 for HTMX attributes).

**Fix:** Use `'#plain_text' => $value` for text. For user HTML use `'#type' => 'processed_text', '#text' => $value, '#format' => $format`. Use Xss::filter() with a minimal tag list for small snippets. Call Markup::create() only on strings built from code and escaped parts.

**Not a finding when:** #markup with string literals, t() output, or values from config editable only by users with a restrict-access admin permission is acceptable. Markup::create() around the result of the renderer or of Html::escape()/Xss::filter() is fine. Always trace where the value comes from before flagging.

**Also covers DSEC-16 (t()/TranslatableMarkup misuse: variable as the string, ! placeholders, @ or % used as a URL).** Signals: `t($var)`, `$this->t($message)`, `t('Hello ' . $name)`, `new TranslatableMarkup($x)`, `formatPlural($count, $var, ...)`; placeholders starting with `!` (`t('!link', ['!link' => ...])`); `t('<a href="@url">')` or `%url` inside an HTML tag; `Drupal.t(variable)` in JS. Not a finding when: t() called on a variable that holds a literal from an annotation/attribute or a constant string array defined in code (for example plugin labels passed through `$this->t($definition['label'])`) is a common and accepted pattern. It is not user input.

### DSEC-17 · User-supplied URL placed as a plain string in href/src (javascript: scheme)

**Severity:** medium · **Area:** security · **Taxonomy:** A05:2025, CWE-79 · **Applies to:** Drupal 10 and 11

### DSEC-24 · SSRF: http_client / Guzzle request to a user-supplied URL

**Severity:** high · **Area:** security · **Taxonomy:** A01:2025, API7:2023, CWE-918 · **Applies to:** Drupal 10 and 11

### DSEC-25 · Unsafe consumption of third-party API responses (no TLS verify, no timeout, rendered as trusted)

### DSEC-26 · unserialize() on data an attacker can influence (PHP object injection)

**Severity:** critical · **Area:** security · **Taxonomy:** A08:2025, CWE-502 · **Applies to:** Drupal 10 and 11

**Signals:** `unserialize(` or `\Drupal::service('serialization.phpserialize')->decode(` on `$_COOKIE`, request parameters, form hidden values, base64-decoded tokens, remote API bodies, uploaded files, or DB columns/fields that users can write; `allowed_classes` given as the only protection; new field types with serialized properties that are writable via JSON:API/REST.

**Why:** Drupal core and common vendor libraries contain gadget chains; with a gadget chain, unserializing attacker data leads to RCE or file deletion. PHP says not to unserialize untrusted input even with allowed_classes. ### DSEC-31 · Custom login, token or password-reset flow with weak tokens, no flood control, or non-constant-time compare

**Severity:** high · **Area:** security · **Taxonomy:** A07:2025, API2:2023, CWE-307, CWE-330, CWE-208 · **Applies to:** Drupal 10 and 11

### DSEC-33 · Sensitive data in logs, or log messages built by concatenation

**Severity:** medium · **Area:** security · **Taxonomy:** A09:2025, CWE-532, CWE-117 · **Applies to:** Drupal 10 and 11

**Signals:** `->logger(...)->info|notice|error|debug(` or `\Drupal::logger(` with `print_r($request->request->all(), TRUE)`, `json_encode($payload)`, `$password`, `$token`, `$apiKey`, `Authorization` headers, full API responses, credit card/PESEL/IBAN fields; messages built with concatenation: `->error('Failed for ' . $input)` or `->error($e->getMessage())` instead of `'@message', ['@message' => ...]`.

**Why:** Logs are kept for a long time, shipped to third parties (New Relic, Sentry, syslog) and readable by more people than the data they contain. Log messages are templates with placeholders, so concatenated user input can also forge or corrupt log entries.

**Fix:** Log identifiers, not payloads: `$this->logger->error('Payment @id failed: @code', ['@id' => $id, '@code' => $code])`. Mask tokens (last 4 characters). For exceptions use `Error::logException($this->logger, $e)` or pass the message as a placeholder.

**Not a finding when:** Logging entity IDs, usernames and status codes is fine. print_r in log calls inside drush commands or dev-only debug branches is lower risk. `$e->getMessage()` passed as a placeholder value is fine.

**Sources:** https://top10.owasp.org/2025/A09_2025-Security_Logging_and_Alerting_Failures/ · https://api.drupal.org/api/drupal/core!lib!Drupal!Component!Render!FormattableMarkup.php/function/FormattableMarkup::placeholderFormat/11.x

### DSEC-34 · Fail-open exception handling in access, validation, signature or payment code; exception text shown to users

**Severity:** high · **Area:** security · **Taxonomy:** A10:2025, CWE-636, CWE-209 · **Applies to:** Drupal 10 and 11

**Signals:** `catch (\Exception $e) { return AccessResult::allowed(); }`, `catch (...) { return TRUE; }` inside access checkers, validators, webhook signature checks or payment callbacks; `@` error suppression on openssl_verify / hash functions; `messenger()->addError($e->getMessage())`, `new JsonResponse(['error' => $e->getMessage()])`, `$e->getTraceAsString()` in responses.

**Why:** When an error path grants access or skips validation, attackers only need to trigger the error (bad input, a timeout on an upstream service) to get in. Exception messages often contain SQL, paths or credentials.

**Fix:** Fail closed: return `AccessResult::forbidden()` or throw, log with Error::logException, and return a generic message to the client. Make sure multi-step operations roll back (`$transaction->rollBack()` or let the exception propagate out of the transaction).

**Not a finding when:** Catching an exception to show a friendly generic message while still denying the action is correct. Showing exception details inside admin-only UIs or drush output is acceptable.

**Sources:** https://top10.owasp.org/2025/A10_2025-Mishandling_of_Exceptional_Conditions/

### DSEC-35 · Custom API endpoint without limits on page size, batch size or expensive operations

**Severity:** medium · **Area:** security · **Taxonomy:** API4:2023, API6:2023, CWE-770 · **Applies to:** Drupal 10 and 11, including GraphQL 4.x producers

**Signals:** Controllers, REST resources or GraphQL producers reading `limit`, `per_page`, `items_per_page`, `range`, `first`, `ids[]` from input and passing them to `->range(0, $limit)` or `loadMultiple($ids)` without a max; anonymous routes that send mail, generate PDFs/images, call paid APIs or create entities without flood control.

**Why:** One request can load thousands of entities, exhaust memory and PHP workers, run up third-party API costs, or flood mailboxes. This gets worse as the data grows.

**Fix:** Clamp: `$limit = min((int) $request->query->get('limit', 20), 100);`. Cap the size of ID arrays. Use the flood service on anonymous side-effect endpoints.

**Not a finding when:** Admin-only exports that run as batch or queue jobs are fine. Endpoints whose limit is capped in a shared paginator service are fine. Views displays have their own pager config, which is out of scope here.

**Also covers DPERF-32 (JSON:API or custom REST exposes unbounded include chains or unpaged collections).** Signals: Drupal side: jsonapi_extras / jsonapi_defaults resource config with multi-level default include paths (a.b.c) in config/sync/jsonapi_extras.jsonapi_resource_config.*.yml, or an added jsonapi_page_limit module or config that raises the page limit above 50. Also a custom ResourceBase or controller returning all entities of a type with no page limit. Also relationship fields newly exposed with large cardinality (unlimited entity references) on public resources. Consumer side (Next.js or other clients in the same diff): include= strings with three or more dotted levels in fetch URLs. Not a finding when: Includes of single-cardinality references (author, image) are cheap. Deep includes on low-traffic internal endpoints are acceptable. Core JSON:API collections are already paged (OffsetPage::SIZE_MAX = 50), so do not flag plain /jsonapi/node/article collection calls.

**Sources:** https://api-security.owasp.org/editions/2023/en/0x11-t10 · https://api.drupal.org/api/drupal/core!lib!Drupal!Core!Flood!FloodInterface.php/interface/FloodInterface/11.x · https://www.drupal.org/docs/core-modules-and-themes/core-modules/jsonapi-module/includes · https://www.drupal.org/project/jsonapi_page_limit · https://www.drupal.org/project/jsonapi_defaults · https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/

### DSEC-36 · OS command or code execution with user-influenced input

**Severity:** critical · **Area:** security · **Taxonomy:** A05:2025, CWE-78, CWE-95 · **Applies to:** Drupal 10 and 11

**Signals:** `exec(`, `shell_exec(`, `system(`, `passthru(`, `proc_open(`, `popen(`, backticks, `Process::fromShellCommandline(` with interpolated variables; `eval(`, `create_function(`; `call_user_func($request->get(...))`, `$class = $input; new $class`, `$this->{$method}()` with a user-chosen method.

**Why:** Direct remote code execution, which means full server compromise.

**Fix:** Avoid shelling out. If you must, use `new Process(['convert', $validatedPath, $out])` (array form, no shell) and validate arguments against an allowlist. Map user choices to callables in code.

**Not a finding when:** Drush commands and deploy scripts with constant arguments are fine. Symfony Process with an array argument list and validated file paths is fine.

**Sources:** https://top10.owasp.org/2025/A05_2025-Injection/ · https://cwe.mitre.org/data/definitions/78.html

### DSEC-37 · Views config opening data: access type none or disable_sql_rewrite

**Severity:** medium · **Area:** security · **Taxonomy:** A01:2025, CWE-862 · **Applies to:** Drupal 10 and 11 (views.view.*.yml in config sync or module config/install|optional)

**Signals:** views.view.*.yml diffs with `access: type: none`, `query: ... options: disable_sql_rewrite: true`, REST export displays (`display_plugin: rest_export`) exposing user/order/webform-like entities or fields such as mail; `accessCheck(FALSE)` in custom Views plugins.

**Why:** `access: none` makes the display public regardless of role. disable_sql_rewrite turns off node access and other query alters, so unpublished and restricted content shows up. REST export displays are an easy way to publish JSON with PII.

**Fix:** Use `access: type: perm` with an appropriate permission (or role). Keep disable_sql_rewrite false unless the view is admin-only. Remove sensitive fields from REST exports, or restrict the display.

**Not a finding when:** Public views of published content can use access none when the entity query itself filters on status and grants; this is very common in projects, so flag only when the view lists non-public data, a REST export, or a user/order entity. Admin views under /admin with a permission gate may use disable_sql_rewrite for performance. Views field handlers normally apply field access, so an exported user mail field is not automatically exposed (not verified this session).

**Sources:** https://www.drupal.org/docs/8/core/modules/views · https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/

### DSEC-38 · Composer changes that weaken the supply chain or pin core/contrib below a security release

**Severity:** medium · **Area:** security · **Taxonomy:** A03:2025, CWE-1104, CWE-829 · **Applies to:** Drupal 10 and 11 (composer.json / composer.lock / patches files)

**Signals:** composer.lock lowering drupal/core or drupal/core-recommended, or leaving them below the current SA fix (the skill must run `composer audit` or compare with https://www.drupal.org/security at review time); `"minimum-stability": "dev"` without `prefer-stable`; `dev-*` or `*` constraints on contrib; composer-patches entries fetched from non-drupal.org URLs or gists; `"secure-http": false`; `"allow-plugins": true` (all plugins); `config.audit.block-insecure: false`, new entries in `audit.ignore`, or `COMPOSER_NO_AUDIT`; new packages from unknown vendors or VCS repositories.

**Why:** Sites get compromised through known core/contrib vulnerabilities more than through custom code (SA-CORE-2026-004 was exploited in the wild on PostgreSQL sites). Remote patch URLs and dev branches can change under you without review. Composer 2.9+ blocks packages with known advisories by default, so turning that off is a deliberate weakening.

**Fix:** Keep core on a supported minor at the latest patch release. Store patches locally in the repo, or reference drupal.org MR diffs pinned to a commit and review them. Allowlist Composer plugins by name. Use `composer audit` in CI and keep audit.block-insecure enabled; drop roave/security-advisories as a required guard on Composer 2.9+.

**Not a finding when:** A dev-branch pin with a comment pointing to a drupal.org issue, pending a release, is a conscious trade-off; flag it low. Patches from git.drupalcode.org stored locally are fine. An audit.ignore entry with a written reason and expiry is acceptable. Reference data as of 2026-09-29 (verified): 10.5.12/10.6.11/11.2.14/11.3.12 fix SA-CORE-2026-005/007/008/009; 11.3.14/11.4.4 fix SA-CORE-2026-011 (11.2.x has no fix); 10.4.10/10.5.10/10.6.9/11.1.10/11.2.12/11.3.10 fix SA-CORE-2026-004 (PostgreSQL only). Do not hard-code these into the skill; they go stale monthly.

**Also check:** Composer audit weakening: `config.audit.block-insecure: false`, growing `audit.ignore`, or CI removing `composer audit`. Partly folded into DSEC-38 but deserves its own quick check. Source: https://getcomposer.org/doc/06-config.md

**Also check:** Supply-chain check for Drupal contrib on the seam: composer.lock bumps or downgrades of drupal/simple_oauth (below 6.0.7), drupal/decoupled_router (below 8.x-1.2), drupal/graphql, drupal/jsonapi_extras, drupal/next against open security advisories. https://www.drupal.org/sa-contrib-2025-114

**Sources:** https://top10.owasp.org/2025/A03_2025-Software_Supply_Chain_Failures/ · https://www.drupal.org/security/core · https://www.drupal.org/sa-core-2026-004 · https://getcomposer.org/doc/06-config.md · https://blog.packagist.com/composer-2-9/
